# Synchronous OpenAI Images migration contract (v0.23)

This document is the source-backed contract for migrating the synchronous OpenAI-compatible Images endpoints to Cloudflare Workers without a Container. The Go handler/service and their tests define the behavioral baseline; committed Worker v0.21 gateway/media code defines the implementation constraints. “External” below means behavior visible to callers or required to preserve correct routing/accounting.

## Current Worker boundary

The historical v0.21 baseline below explains the gaps this contract was written against. v0.22 shipped direct API-key synchronous Images; v0.23 adds Codex OAuth-like Responses execution, bounded Responses-SSE conversion, buffered Images JSON, protocol-compatible collected Images SSE, and semantic retry/failover decisions. Live incremental forwarding, persisted setup-token identity, adapter-specific account-model capability, and direct-provider streaming are still not complete compatibility.

- `app.ts` registers only the batch `/v1/images/batches` family, not synchronous generations/edits ([worker/src/app.ts:735](../src/app.ts#L735)).
- The generic gateway endpoint union contains only Chat Completions, Responses, and Embeddings ([worker/src/gateway/types.ts:7](../src/gateway/types.ts#L7)); provider operations have no OpenAI Images operation ([worker/src/gateway/providers/index.ts:10](../src/gateway/providers/index.ts#L10)).
- The generic body reader is JSON-only and capped at 2 MiB, so it cannot be reused as the multipart Images parser ([worker/src/gateway/request-body.ts:6](../src/gateway/request-body.ts#L6), [worker/src/gateway/request-body.ts:27](../src/gateway/request-body.ts#L27)).
- Migration 0043 already provides `allow_image_generation`, 1K/2K/4K prices, image-rate policy, and R2-backed batch task tables ([worker/migrations/0043_media_tasks.sql:3](../migrations/0043_media_tasks.sql#L3)). Its batch provider is Gemini-only, requires `allow_batch_image_generation`, deterministically picks one account, and has no Pool failover; it is infrastructure to reuse selectively, not synchronous compatibility ([worker/src/media/repository.ts:54](../src/media/repository.ts#L54), [worker/src/media/provider.ts:44](../src/media/provider.ts#L44)).
- The generic gateway already has useful Worker-native primitives: API-key admission, three monetary/quota reservations, Pool Durable Object leases/failure cooldown, settlement recovery, and bounded disconnect draining ([worker/src/gateway/handler.ts:1054](../src/gateway/handler.ts#L1054), [worker/src/gateway/handler.ts:1482](../src/gateway/handler.ts#L1482), [worker/src/gateway/handler.ts:2500](../src/gateway/handler.ts#L2500)). v0.22 should share these primitives rather than fork a second billing/scheduling authority.

Uncommitted synchronous-image work in the working tree is not acceptance evidence. Only the tests named under the vertical slices can move this surface from Pending to compatible.

## Status vocabulary

- **Retain** — preserve this behavior in the Worker and lock it with a parity test; it does not mean v0.21 already implements it.
- **Replace** — intentionally change the Go behavior; the replacement is the proposed contract.
- **Remove** — do not migrate this behavior as part of synchronous Images.
- **Pending** — evidence is insufficient or the choice depends on Worker/runtime/product constraints; resolve before declaring parity.

v0.22 moderation decision: a configured Worker moderator remains the pre-admission policy gate. When no such binding exists, the direct OpenAI adapter overwrites the upstream option with `moderation=auto`; callers cannot downgrade it to `low`. This is a concrete provider-enforced fallback rather than an unmoderated production path. A future local model/binding may strengthen preflight behavior without changing the public API.

v0.22 lifecycle decision: after an account lease is acquired, the Worker pins the bounded provider/body/settlement/cleanup lifecycle with `waitUntil` and renews API-key plus Pool leases on the shared 20-second cadence. Settlement first writes the D1 recovery row; if D1 is unavailable, it sends a complete immutable `settlement.command.v1` payload to Cloudflare Queue so retries do not depend on a missing row.

## Exit criteria

Parity is complete only when every **Retain** row has a passing Worker test, every **Replace** row has a test proving both the new behavior and rejection of the legacy hazard, every **Remove** row has a non-invocation test or explicit architecture note, and every **Pending** row is converted to one of the other three statuses. The disconnect/billing test must verify durable exactly-once settlement after the caller is gone; response-only tests are insufficient.
